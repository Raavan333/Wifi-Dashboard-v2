# WIFI OBSERVABILITY & INVESTIGATION PLATFORM
## PHASE 3 BACKEND EVOLUTION SPECIFICATION

This document supersedes all previous enhancement requests.

The current backend is already operational and largely validated.

The goal is NOT to rewrite the backend.

The goal is to evolve the platform from:

```text
Dashboard
+
Entity Endpoints
```

into:

```text
Dashboard

+
Investigation Engine

+
Entity Graph

+
Observability Layer

+
Network Intelligence Platform
```

without breaking existing APIs.

# P0 - VALIDATED DEFECTS

These are correctness or platform issues and should be addressed before building new capabilities.

---

## DEFECT-001

Recovery Analysis

Current implementation:

```text
~39 seconds
```

Cause:

```sql
7.4M row scan

GROUP BY user_mac
```

Required:

Recovery state must be materialized and maintained during the existing incremental summary update process.

Suggested fields:

```sql
recovered_after_failure BOOLEAN

first_fail_timestamp TIMESTAMPTZ

last_success_after_fail TIMESTAMPTZ
```

Recovery must remain exact.

Do not replace with heuristics.

---

## DEFECT-003

Active User Trend

Current runtime:

```text
~13.6 seconds
```

Cause:

Daily aggregation over event history.

Required:

Introduce daily aggregation table.

Examples:

```text
daily_active_users

daily_user_statistics
```

Dashboard must consume summary data.

---

## DEFECT-004

UX Missing counts differ between endpoints.

Required:

One canonical definition:

```sql
ux_available = false
```

must be used platform-wide.

---

## DEFECT-005

Valid User classification mismatch.

Current:

```text
Expected
10508

Returned
11029
```

Cause:

Device count used instead of user count.

Required:

Valid User means:

```sql
COUNT(DISTINCT employee_id)

WHERE

employee_id IS NOT NULL
AND total_success_count >= 1
```

---

## DEFECT-006

Inactive Users uses:

```sql
NOW()
```

Required:

Reference timestamp should derive from:

```sql
MAX(last_seen_timestamp)
```

within current dataset.

# P4 - FRONTEND EFFICIENCY SUPPORT

Entity APIs should return enough context to avoid N+1 API calls.

Example:

```text
SSID View

already includes:

Locations

APs

Metrics
```

Continue this philosophy everywhere.

Frontend should rarely require more than:

```text
one entity API
```

to render an investigation panel.

```text
WiFi Observability Platform

Network Intelligence

+
Entity Graph

+
Investigation Engine

Time-Series Analytics
```
